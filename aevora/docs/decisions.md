# Decisions

The decisions that shape the engine and the game it's being built for, from the design discussion, and what's still open. The order of work is in [roadmap.md](roadmap.md).

## Decided

### How the engine is built

- **Terrain in memory:** a layered heightmap. Each column holds a short list of solid spans (floor and ceiling heights), so digging, water, dirt thickness, and collision all work per column, underground as well as on the surface. Curves are carved into it by removing a vertical interval from each column they pass through. The grid sits on a cube mapped onto the sphere, with columns pointing at the planet's center. If cave walls look too coarse, those chunks can be meshed in 3D from the same curves instead; compare the two before digging is built, since how edits are saved depends on it.
- **Grid on the sphere:** a cube sphere, with face coordinates spaced by angle so cells stay close to the same size. The generator must orient the cube so all 8 corners land in deep ocean, where there is no terrain to get wrong.
- **Terrain source of truth:** the height function from the planet generator, the curve features, and the player's edits. Everything else is built from these.
- **Shader language:** HLSL, compiled for Vulkan now and for DirectX 12 later from the same source. It also suits Xbox, PlayStation, and Mac ports. Valuma's shaders stay GLSL.
- **Mods:** data and assets, downloaded automatically on join. Sandboxed scripts later. No downloaded native code.
- **Terrain:** a heightmap surface, plus features defined by curves with weights. Caves remove rock along curves; overhangs, arches, and cliff lips add it. No predefined pieces for these.
- **Graphics API:** Vulkan alone for now, behind an interface designed so DirectX 12 can be added.
- **Networking:** ownership. A client owns its own movement and whatever it's nearest to; the server relays, checks, and saves. "The server owns everything" stays possible as a setting.

### The game
- Open-world survival crafting, PvE first with optional PvP, medieval fantasy, Studio Ghibli look.
- Up to about 10 players if networking allows; players can be anywhere on the planet.
- Each client is responsible for its own actions; the host shouldn't have to simulate for others. Clients are trusted, with simple server checks.
- First and third person.
- Melee, ranged, and magic combat, tighter than Valheim (subject to testing).
- Building is a core feature and must stay fast for very large bases: large and varied pieces, multithreading, every optimization available.
- Speeds being tried in the curvature test: walking 20 km/h, running 32, a ground mount 100 (130 at a push), a dragon cruising at 180 (250 in bursts). Fast travel exists but cuts to an animation.
- Boats and diving; oceans have real content.
- Many creature kinds per biome; about 100 alive near a player.
- Seasons, with creatures migrating. The world changes without players nearby, but only back toward what it was generated as: crops grow, cut forests regrow by time away. Mountains, rivers, and erosion never change after generation.

### The planet
- The planet is sized so a dragon at cruising speed takes an hour to go around: at 180 km/h that is 180 km around, a radius of about 28.6 km. It is drawn to look like a planet of about 200 km radius. Fixed for players, adjustable for the developer.
- 65 to 72% ocean. Ocean biomes (reefs, shores, deep ocean) with climate variants. Deep ocean has no floor; going too deep kills.
- Underground as deep as testing allows, not to the core.
- Poles walkable. Gravity points at the center.
- A real sun, so time of day differs around the planet. Axial tilt and seasons, with polar day and polar night. A moon and stars; no other planets, no leaving.

### Terrain
- Looks like Valheim, with caves and overhangs. Not voxels.
- Minimal edits only: dig a bit, flatten a bit.
- Layers: dirt over rock, ores hidden inside or exposed in caves.
- Lakes and rivers at different heights. Water flows and reacts to digging in a simple way; a small pond can be moved with a bucket.
- Caves generated by rules. Hand-made places are stamped into the generated world.
- Heavy level-of-detail work so the horizon reads as unlimited view distance.

### Generation
- A simplified simulation on coarse maps, run once: 1 to 2 minutes on good hardware, 3 to 5 on weak.
- Erosion is part of generation only.
- Rivers flow correctly from mountains to lakes to the sea. Lakes have one exit; rivers only join, never split.
- Same seed gives the same world on every machine.
- Many biomes, added over time, with soft transitions and sub-biomes.
- Trees and rocks placed by biome rules; each one persists (cut stays cut, planted stays planted).
- Base biomes can't be edited by hand. Mask biomes sit over base biomes, can spread, and can be edited.
- Players get a seed plus sliders or presets.

### Rendering
- Target: GTX 1600 series and up.
- Sun and moon as directional lights, a limited number of local lights, shadows from both.
- Weather and storms exist at places on the planet and follow climate; clouds, rain, snow, and fog match them.
- Ocean varies with wind from calm to large storm waves; lakes are simple with some chop. Reflections and an underwater view.
- Ghibli-style vegetation with heavily optimized grass.
- Valuma's current material is enough for now.
- Post effects, chosen through testing.

### Multiplayer
- Listen server and dedicated server from the same code. Single player runs the same code locally.
- Clients generate terrain from the seed.
- Characters live on the player's machine and move between worlds.
- Text chat only.
- Mods are supported; a client joining a modded server downloads what it needs automatically.

### Game code
- C++ in its own library with hot reload.
- Entity component system.
- Own physics, kept separate enough to swap for a library if it proves too much.
- Everything from scratch.
- Fixed 60 per second for physics and timing; rendering runs faster.
- Coarse simulation away from players.
- A job system early; multithreading throughout.

### Editor
- Play inside the editor from the start. Values are read-only during play unless marked editable.
- Edits scenes, data, and generation rules. Workspaces like Valuma's tabs. Full undo.
- Assets reload when re-exported; "open in Valuma" on an asset.
- As much profiling and debug tooling as possible.
- Launch several players on one machine for multiplayer testing.

### Sites, gyms, zoos, museums
- Zoos and museums are generated from data by a button or setting, with marks for which data and tests are shown.
- Gyms show anything a developer references constantly; measurements are checked automatically.
- Rooms don't use the planetary look. Sites aren't opened from a spot on a real planet.
- These are developer scenes; the game itself is the one world.

### Assets, files, platform
- `.vlmobj` gains skeletons, animation, collision shapes, levels of detail, and sockets before the game is built. Rigging and animation are built in Valuma first.
- Collision: simple shapes from Valuma, with a per-triangle option for static things.
- Levels of detail come from Valuma; Aevora adds its own for terrain and for groups (many trees as one).
- No audio for now; an importer once a format is chosen.
- The game's UI is a separate, more styled system than the editors'.
- English for now.
- A project is a folder; `.aev` is the project file. Text for data and scenes, baked to binary for the game.
- World saves are seed plus changes (to be confirmed by testing). Early versions may break saves; later ones must not.
- The game project is its own repo.
- Windows and Linux; consoles and Mac someday.
- Each piece is built to keep.

- Local light limits and any global lighting.
- Creature AI approach.
- Site parameters and size.
- Texture formats and sizes.
- How biome rules are written (code, data, or both).
- How a system declares what it syncs.
- Test strategy beyond unit tests.
